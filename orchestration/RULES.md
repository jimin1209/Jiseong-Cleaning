# 지성크리닝 웹사이트 개편 — 오케스트레이션 규정 (RULES)

## 0. 체계

- **오케스트레이터(메인)**: Claude Code 메인 세션. 세션 소환·검수·병합·순서 결정을 전담한다.
- **워커 세션**: `claude --dangerously-skip-permissions -p` 로 소환되는 헤드리스 세션. 자신의 지시서(`sessions/S*.md`) 범위만 수행한다.
- **기준 문서(SSOT)**: `/home/jimin/지성크리닝-상세-요구사항-명세.md` — 모든 문구·구조 결정의 단일 출처. 지시서와 명세가 충돌하면 **명세가 우선**하고, 충돌 사실을 핸드오프에 기록한다.
- 작업 디렉토리: `/home/jimin/Jiseong-Cleaning/website`

## 1. 세션 공통 수칙

1. **범위 엄수**: 지시서에 명시된 파일·작업만 수정한다. 범위 밖 문제를 발견하면 고치지 말고 핸드오프의 `발견사항`에 기록한다.
2. **결정 금지**: 명세에 없는 문구·기능을 창작하지 않는다. 판단이 필요한 지점은 핸드오프의 `질문`에 기록하고, 임시 처리한 경우 그 사실을 명시한다.
3. **용어 규칙 절대 준수**: 납품→배송(배달 금지), 린넨→세탁물, 고온·온수 삭제, 업소용→전문, "약속한 날짜", 부정 표현 금지, "24시간" 금지, 가짓수 표현 금지, "고정 시간" 금지, "세탁일지·위생관리 기록" 금지. 새로 쓰는 문구에도 적용된다.
4. **한국어**: 코드 주석·커밋 메시지·핸드오프 전부 한국어.
5. **코드 스타일**: 기존 코드의 주석 밀도·네이밍·패턴을 따른다. `lib/site.ts` 단일 출처 원칙(상호·전화·주소는 직접 쓰지 않고 site에서 가져옴)을 유지한다.
6. **더미 데이터**: 반드시 `lib/sample.ts` 한 곳에서 관리. 그럴싸한 가짜 번호·이름을 새로 짓지 않는다(기존 원칙).

## 2. 검증 의무 (세션 종료 조건)

세션은 아래를 **모두 통과해야** 핸드오프를 쓰고 종료할 수 있다:

```bash
npx next build          # 빌드 성공 (오류 0)
```

추가로 자기 범위에 해당하는 검증:
- 용어 스윕 담당: `grep -rn "납품\|린넨\|리넨\|고온\|업소용\|취급하지\|천북\|054-621" src/` 결과 0건 (schema.ts 주석 제외 불가 — 주석도 고친다)
- 구조 담당: 삭제한 라우트가 sitemap·nav·footer 어디에도 남지 않음
- 폼 담당: 폼 제출 경로(스키마 검증) 통과 확인

## 3. Git·워크트리 규칙

1. **세션마다 전용 워크트리·브랜치**를 쓴다. 오케스트레이터가 소환 전에 만들어 준다:
   - 워크트리: `/home/jimin/Jiseong-Cleaning/wt/<세션ID>` (작업 디렉토리는 그 아래 `website/`)
   - 브랜치: `work/<세션ID>` — 통합 브랜치 `redesign/2026-08-28` 에서 분기
2. 워커는 **자기 워크트리 밖의 파일을 수정하지 않는다** (핸드오프는 예외: 메인 레포의 `orchestration/handoffs/`에 쓴다).
3. 세션 종료 시 **자기 세션 ID를 머리말로 커밋**: 예) `S1: 전역 값 교체 및 용어 일괄 치환`. 커밋 안 된 변경을 남기지 않는다.
4. **merge·rebase·push 금지**. 검증·병합·충돌 해소·푸시는 전부 오케스트레이터가 한다.
5. 다른 세션의 커밋·워크트리를 건드리지 않는다.

## 3-1. 오케스트레이터 의무 (통합 게이트)

각 세션 종료 후 오케스트레이터가 직접:
1. 핸드오프 검토 + `git log`/`git diff` 로 범위 준수 확인
2. **명세 대조 검증**: 해당 세션 범위의 요구사항이 실제 반영됐는지 grep/코드 확인
3. `work/<세션ID>` → `redesign/2026-08-28` 병합 (충돌은 오케스트레이터가 해소)
4. 병합 후 `npx next build` 재확인
5. STATUS.md 갱신 → 다음 세션 브랜치를 최신 통합 지점에서 분기해 소환
불합격 시 병합하지 않고 보완 지시와 함께 같은 세션을 재소환한다.

## 4. 핸드오프 규칙

- 세션 종료 직전 `orchestration/handoffs/<세션ID>-handoff.md` 를 `HANDOFF-TEMPLATE.md` 형식으로 작성한다. **핸드오프 없는 종료는 실패로 간주**한다.
- 핸드오프는 다음 세션이 읽는 유일한 인수인계 문서다. "코드를 보면 안다"는 금지 — 변경 요지·미완료·질문을 명시한다.
- 세션 시작 시 자신보다 앞선 세션의 핸드오프를 전부 읽고 시작한다.

## 5. 실행 순서 (의존성)

```
S1 전역값·용어치환 ──▶ S2 구조 개편 ──▶ S3 페이지 문구 ──▶ S4 폼 5레이어 ──▶ S5 신규 기능 ──▶ S6 최종 검증·QA
```

- 워크트리로 격리되므로 오케스트레이터 판단에 따라 파일 겹침이 적은 세션(예: S2 구조 ∥ S3 폼)은 병렬 소환 가능. 병합 순서와 충돌 해소는 오케스트레이터 책임.
- 각 세션 실패 시: 오케스트레이터가 로그·핸드오프를 검토해 같은 세션을 보완 지시와 함께 재소환한다. 다음 세션으로 넘어가지 않는다.

## 6. 금지 사항

- `next.config.ts`의 배포 설정, `netlify.toml` 변경 금지 (S6 검증에서 필요 시 오케스트레이터 승인)
- 패키지 추가/삭제 금지 (필요하면 핸드오프에 질문으로 남김)
- `Document/` 폴더, 레포 루트의 회의 문서 수정 금지
- 명세의 "확인 대기(G/블로킹)" 항목을 임의로 확정하지 않음 — 더미+추적 목록으로 처리

## 7. 에스컬레이션

워커가 스스로 판단할 수 없는 경우(빌드가 지시 이행과 양립 불가, 명세 내 모순 발견 등):
1. 작업을 안전한 지점까지 커밋
2. 핸드오프 `질문` 절에 상황 기술
3. 정상 종료 (오케스트레이터가 판단 후 재지시)
