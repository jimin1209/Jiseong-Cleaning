# 04. 주문 상태 머신

> 이 문서가 **시스템 전체의 중심**이다. 고객·기사·공장·관리자 화면이 전부 이 상태를 기준으로 동작한다.
> 구현 시 `packages/shared/src/order-state.ts` 한 파일에 상수와 전이표를 두고 web/api가 공유한다.

---

## 1. 정상 흐름 (Happy Path)

```
                  [고객]                [관리자]              [기사]
DRAFT ──신청──▶ REQUESTED ──배차──▶ SCHEDULED ──출발──▶ PICKUP_ON_THE_WAY
   임시저장        수거 신청됨          기사 배정됨            수거하러 가는 중
                                                                │ 수거완료
                                                                ▼
                                                           PICKED_UP
                                                            수거 완료
                                                                │ 공장 입고
             [공장]                                             ▼
        ┌────────────────────────────────────────────── AT_FACTORY
        │                                                  공장 입고됨
        │ 검수
        ▼
   INSPECTED ──(추가금 있음)──▶ AWAITING_APPROVAL ──고객승인──┐
   검수 완료                       고객 승인 대기               │
        │                                                       │
        └──(추가금 없음)────────────────────────────────────────┤
                                                                ▼
                                                            WASHING
                                                             세탁 중
                                                                │
                                                                ▼
                                                             READY
                                                          포장완료·출고대기
                                                                │ 기사 출고
             [기사]                                             ▼
                                                    DELIVERY_ON_THE_WAY
                                                          배송 중
                                                                │ 배송완료
                                                                ▼
                                                           DELIVERED
                                                           배송 완료
                                                                │ 결제 확정 (자동)
                                                                ▼
                                                           COMPLETED
                                                             거래 완료
```

## 2. 전체 상태 목록

### 정상 상태
| 코드 | 고객에게 보이는 문구 | 의미 |
|---|---|---|
| `DRAFT` | (표시 안 함) | 임시저장 |
| `REQUESTED` | 수거 신청 완료 | 접수됨, 배차 대기 |
| `SCHEDULED` | 기사 배정 완료 | 담당 기사 지정됨 |
| `PICKUP_ON_THE_WAY` | 수거하러 가는 중 | 기사 출발 |
| `PICKED_UP` | 수거 완료 | 세탁물 인계됨 |
| `AT_FACTORY` | 세탁소 도착 | 공장 입고 |
| `INSPECTED` | 검수 완료 | 최종 금액 확정 |
| `AWAITING_APPROVAL` | **추가 금액 확인 필요** | 고객 승인 대기 (알림 발송) |
| `WASHING` | 세탁 중 | |
| `READY` | 세탁 완료 · 배송 준비 | 포장 완료 |
| `DELIVERY_ON_THE_WAY` | 배송 중 | |
| `DELIVERED` | 배송 완료 | |
| `COMPLETED` | 완료 | 결제 확정 |

### 예외 상태
| 코드 | 고객 문구 | 의미 | 복귀 가능? |
|---|---|---|---|
| `PICKUP_FAILED` | 수거 실패 (부재) | 고객 부재/주소 오류 | ✅ → `SCHEDULED` 재배차 |
| `DELIVERY_FAILED` | 배송 실패 (부재) | | ✅ → `READY` 재배차 |
| `ON_HOLD` | 처리 보류 | 손상 발견 등 관리자 개입 필요 | ✅ → 직전 상태 |
| `QUOTE_REJECTED` | 추가금 미승인 | 고객이 추가금 거절 | ✅ → 원상 반송 or 협의 |
| `RETURNED` | 세탁 불가 · 반송 | 공장이 세탁 불가 판정 | ❌ 종결 |
| `CANCELED` | 취소됨 | | ❌ 종결 |
| `REFUNDED` | 환불 완료 | | ❌ 종결 |

## 3. 전이 권한 매트릭스

| From → To | 실행 주체 | 조건 / 필수 입력 |
|---|---|---|
| `DRAFT` → `REQUESTED` | 고객 | 주소·날짜·슬롯·품목 필수, 슬롯 정원 여유 확인 |
| `REQUESTED` → `SCHEDULED` | 관리자 (또는 자동배차) | `assignments`(PICKUP) 생성 |
| `REQUESTED` → `CANCELED` | 고객 / 관리자 | 무료 취소 |
| `SCHEDULED` → `PICKUP_ON_THE_WAY` | 기사 | assignment 소유자만 |
| `SCHEDULED` → `CANCELED` | 고객 / 관리자 | 수거 당일 취소 시 정책 따름 |
| `PICKUP_ON_THE_WAY` → `PICKED_UP` | 기사 | **사진 1장 이상 필수**, 봉투 수량 입력 |
| `PICKUP_ON_THE_WAY` → `PICKUP_FAILED` | 기사 | 실패 사유 필수 + 사진(문앞 확인) |
| `PICKUP_FAILED` → `SCHEDULED` | 관리자 | 재배차 |
| `PICKUP_FAILED` → `CANCELED` | 관리자 | |
| `PICKED_UP` → `AT_FACTORY` | 기사 / 공장 | QR 스캔 입고 |
| `AT_FACTORY` → `INSPECTED` | 공장 | **`qty_confirmed` 전 품목 입력 필수** → `final_amount` 계산 |
| `INSPECTED` → `AWAITING_APPROVAL` | 시스템(자동) | `final_amount > estimated_amount × 1.1` 이거나 신규 품목 추가 시 |
| `INSPECTED` → `WASHING` | 시스템(자동) | 위 조건 미해당 시 즉시 진행 |
| `AWAITING_APPROVAL` → `WASHING` | 고객 | 승인 → `quote_approved_at` 기록 |
| `AWAITING_APPROVAL` → `QUOTE_REJECTED` | 고객 | 거절 |
| `AWAITING_APPROVAL` → `WASHING` | 관리자 | 전화로 구두 승인받은 경우 (사유 필수, 감사로그) |
| `QUOTE_REJECTED` → `WASHING` | 관리자 | 협의 완료 후 |
| `QUOTE_REJECTED` → `READY` | 관리자 | 세탁 없이 원상 반송 |
| `WASHING` → `READY` | 공장 | `factory_jobs.stage = PACKING → READY` |
| `AT_FACTORY`/`WASHING` → `RETURNED` | 공장 | 세탁 불가 사유 + 사진 필수 |
| `READY` → `DELIVERY_ON_THE_WAY` | 기사 | 배송 assignment 필요 (관리자 배차 선행) |
| `DELIVERY_ON_THE_WAY` → `DELIVERED` | 기사 | **사진 필수** (비대면) 또는 서명 (대면) |
| `DELIVERY_ON_THE_WAY` → `DELIVERY_FAILED` | 기사 | 사유 필수 |
| `DELIVERY_FAILED` → `READY` | 관리자 | 재배차 |
| `DELIVERED` → `COMPLETED` | 시스템(자동) | 결제 성공 시 즉시. 결제 실패 시 `DELIVERED` 유지 + 관리자 알림 |
| 임의 → `ON_HOLD` | 관리자 | **사유 필수**, 감사로그 기록 |
| `ON_HOLD` → 직전 상태 | 관리자 | |
| 임의 → 임의 | 관리자(SUPER) | **강제 전이. 사유 필수 + 감사로그 + 알림** |

## 4. 구현 규칙

### 4.1 상태 전이는 단일 서비스 메서드로만
```ts
// order-state.service.ts
async transition(orderId, toStatus, actor, payload) {
  return this.prisma.$transaction(async (tx) => {
    const order = await tx.order.findUnique({ where: {id: orderId} });

    // 1) 전이표에 있는 조합인가
    assertTransitionAllowed(order.status, toStatus);
    // 2) 이 사람이 할 수 있는 전이인가 (역할 + 소유권)
    assertActorAllowed(order, order.status, toStatus, actor);
    // 3) 필수 입력이 채워졌는가 (사진, 수량, 사유 …)
    assertRequirements(toStatus, payload);

    await tx.order.update({ where: {id: orderId}, data: {status: toStatus} });
    await tx.orderStatusHistory.create({ data: {...} });  // 항상 기록

    // 4) 부수 효과는 트랜잭션 밖 큐로
    this.events.emit('order.transitioned', { orderId, from, to });
  });
}
```

> **주의:** `order.status = X` 를 여기 말고 다른 곳에서 직접 UPDATE 하지 않는다.
> 컨트롤러·배치·관리자 화면 전부 이 메서드를 거친다. 이걸 어기는 순간 이력이 깨진다.

### 4.2 낙관적 잠금
기사가 버튼을 두 번 누르거나 관리자와 기사가 동시에 바꾸는 경우가 실제로 자주 발생한다.
```
UPDATE orders SET status = 'PICKED_UP', version = version + 1
WHERE id = ? AND status = 'PICKUP_ON_THE_WAY' AND version = ?
→ 영향 행 0건이면 409 Conflict 반환, 클라이언트는 최신 상태 재조회
```
추가로 상태 변경 API는 `Idempotency-Key` 헤더를 받아 5분간 동일 키 요청은 이전 결과를 그대로 반환한다.

### 4.3 전이 시 부수 효과 (이벤트 핸들러)
| 이벤트 | 부수 효과 |
|---|---|
| `→ REQUESTED` | 슬롯 정원 차감 / 고객 알림톡 "접수 완료" |
| `→ SCHEDULED` | 고객 알림 "○○ 기사 배정, 08/09 09-12시" |
| `→ PICKUP_ON_THE_WAY` | 고객 푸시 "기사가 출발했습니다" |
| `→ PICKED_UP` | 고객 알림톡 + 사진 링크 |
| `→ AWAITING_APPROVAL` | **고객 알림톡(강조) + 푸시 + 24시간 후 미응답 시 재알림** |
| `→ READY` | 관리자 배차 대기 목록에 추가 |
| `→ DELIVERED` | 결제 처리 큐 등록 |
| `→ COMPLETED` | 영수증 발송 / **구독 횟수 확정 차감** (문서 06 §2) / 리뷰 요청(3일 후, *2차 기능*) |
| `→ CANCELED` | 슬롯 정원 복구 / 결제 있으면 환불 큐 |
| `→ *_FAILED` | 관리자 대시보드 알림 (즉시 대응 필요) |

### 4.4 SLA 감시 (배치)
| 상태 | 임계 시간 | 초과 시 |
|---|---|---|
| `REQUESTED` | 수거 예정일 전날 18시까지 미배차 | 관리자 알림 |
| `AT_FACTORY` | 24시간 내 미검수 | 관리자 알림 |
| `WASHING` | 표준 소요일 + 1일 초과 | 관리자 알림 + 고객 지연 안내 |
| `AWAITING_APPROVAL` | 48시간 무응답 | 관리자에게 전화 요청 티켓 |
| `READY` | 24시간 내 미배차 | 관리자 알림 |

## 5. 공장 작업 단계 (`factory_jobs.stage`)

주문 상태와 **별개로** 공장 내부 진행도를 따로 관리한다. (주문 상태는 `WASHING` 하나지만
공장 안에서는 여러 단계가 있음)

```
RECEIVED ─▶ INSPECTING ─▶ WASHING ─▶ DRYING ─▶ PACKING ─▶ READY
                 │
                 └─▶ RETURNED (세탁 불가)
```

| factory stage | 대응 order status |
|---|---|
| RECEIVED | AT_FACTORY |
| INSPECTING | AT_FACTORY |
| (검수 완료) | INSPECTED → AWAITING_APPROVAL or WASHING |
| WASHING / DRYING / PACKING | WASHING |
| READY | READY |
| RETURNED | RETURNED |
