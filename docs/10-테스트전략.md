# 10. 테스트 전략

> 전제: **1인 개발**이다. 테스트를 다 쓸 시간은 없다. 그래서 "커버리지 몇 %"가 아니라
> **"틀리면 돈이 새거나 세탁물을 잃어버리는 곳"에만 테스트를 집중한다.**

---

## 1. 우선순위 — 여기부터 테스트한다

| 순위 | 대상 | 틀렸을 때 벌어지는 일 | 테스트 종류 |
|---|---|---|---|
| **1** | 주문 상태 전이표 (문서 04) | 기사가 못 넘김 / 관리자가 임의로 넘김 / 이력 유실 | 단위 (전수) |
| **2** | 금액 계산 파이프라인 (문서 06 §2) | **고객에게 잘못 청구** | 단위 |
| **3** | 구독 횟수 차감 | 횟수가 새거나 이중 차감 | 통합 |
| **4** | 결제 멱등성 | **이중 결제** | 통합 |
| **5** | 권한(소유권) 검사 | 남의 주문 조회·변경 | 통합 |
| **6** | 권역별 슬롯·배송일 계산 (문서 09 §1.2) | 갈 수 없는 날에 예약 접수 | 단위 |
| **7** | 슬롯 정원 동시성 | 정원 초과 예약 | 통합 |
| 8 | 화면 흐름 | 사용 불편 | E2E (핵심 시나리오만) |
| 9 | 나머지 CRUD | — | 안 씀. 타입스크립트에 맡긴다 |

## 2. 테스트 도구

| 계층 | 도구 | 비고 |
|---|---|---|
| 단위 (API) | **Vitest** | Jest보다 빠름. 순수 함수 위주 |
| 통합 (API+DB) | Vitest + **Supertest** + **Testcontainers** | 진짜 Postgres를 컨테이너로 띄움. mock DB 금지 |
| 외부 연동 | **nock** (PG·알림톡 HTTP 목킹) | 토스 테스트키는 E2E에서만 |
| 프론트 단위 | Vitest + Testing Library | 금액 표시·상태 라벨 정도만 |
| 프론트 API 목 | **MSW** | |
| E2E | **Playwright** | 실제 브라우저, 모바일 뷰포트 포함 |
| 부하 | **k6** | 오픈 직전 1회 |

> **Testcontainers를 쓰는 이유:** 이 시스템은 트랜잭션·낙관적잠금·UNIQUE 제약이 핵심 방어선이다.
> DB를 목킹하면 정확히 그 방어선을 테스트하지 못한다.

## 3. 반드시 써야 하는 테스트 (구체 목록)

### 3.1 상태 전이표 — **전수 테스트**

가장 중요하다. 20개 상태 × 20개 상태 × 4개 역할 = 1,600개 조합을 **표 하나로 전부 검증**한다.

```ts
// order-state.spec.ts
import { TRANSITIONS } from '@jiseong/shared/order-state'

const ALL_STATUSES = [...] // 20개
const ALL_ROLES = ['CUSTOMER','DRIVER','FACTORY','ADMIN'] as const

describe('상태 전이표 전수 검증', () => {
  test.each(ALL_STATUSES.flatMap(from =>
    ALL_STATUSES.flatMap(to =>
      ALL_ROLES.map(role => [from, to, role] as const))))
  ('%s → %s (%s)', (from, to, role) => {
    const allowed = isTransitionAllowed(from, to, role)
    // 전이표에 명시된 조합만 true, 나머지는 전부 false여야 한다
    expect(allowed).toBe(TRANSITIONS.some(t =>
      t.from === from && t.to === to && t.actors.includes(role)))
  })
})
```

추가로 반드시 검증할 것:
- [ ] `PICKED_UP` 전이 시 **사진 0장이면 거부**
- [ ] `INSPECTED` 전이 시 **`qty_confirmed` 미입력 품목이 있으면 거부**
- [ ] 관리자 강제 전이 시 **사유 없으면 거부**
- [ ] 모든 성공 전이가 `order_status_history`에 **정확히 1행** 남기는지
- [ ] 종결 상태(`CANCELED`/`RETURNED`/`REFUNDED`)에서 나가는 전이는 **전부 거부**

### 3.2 금액 계산 — 표 기반 테스트

문서 06 §2의 계산 예시 3개를 그대로 테스트 케이스로 만든다. 여기에 경계값을 추가:

| 케이스 | 입력 | 기대 청구액 |
|---|---|---|
| 구독 커버 이내 | 확정 12,000 / 한도 15,000 / 잔여 4 | 0원, 차감 예정 1 |
| 구독 초과 | 확정 28,000 / 한도 15,000 / 할인 10% | 11,700원 |
| 잔여 0 | 확정 20,000 / 잔여 0 / 할인 10% | 18,000원 |
| **정확히 한도** | 확정 15,000 / 한도 15,000 | 0원 |
| **구독 없음** | 확정 20,000 / 구독 null | 20,000원 |
| **품목 제한 플랜** | 셔츠정기권 + 코트 주문 | 코트는 커버 0 |
| **검수 후 금액 감소** | 예상 22,000 → 확정 18,000 | 승인 불필요, 18,000 기준 |
| **원 단위 반올림** | 초과 13,333 × 10% 할인 | 소수점 발생 금지 (int) |
| 0원 | 확정 금액 전액 커버 | 결제 스킵 후 COMPLETED |

> **반올림 규칙을 정하고 테스트로 고정한다.** 할인 계산에서 원 미만이 나오면 **버림**.
> 정하지 않으면 프론트 표시액과 실제 결제액이 1원 어긋나는 사고가 난다.

### 3.3 구독 횟수 — 통합 테스트

문서 06 §2의 3단계 차감 규칙을 그대로 검증한다.

- [ ] `REQUESTED` 시점에 `remaining_count` **변하지 않음**
- [ ] `INSPECTED` 시점에도 **변하지 않음**
- [ ] `COMPLETED` 시점에 **정확히 1 감소**
- [ ] 주문 취소(`CANCELED`) 시 **감소하지 않음** (애초에 안 줄였으므로 복구 로직 없음)
- [ ] 잔여 1인데 **동시에 2건 주문** → 두 번째는 구독 미적용으로 계산
- [ ] 정기결제 성공 시 `remaining_count`가 **플랜 값으로 리셋**(누적 아님)

### 3.4 결제 멱등성 — 통합 테스트

- [ ] 같은 `idempotency_key`로 **2회 호출 → PG 승인 요청은 1회만** (nock 호출 횟수 검증)
- [ ] 동일 주문에 대해 **동시 2요청** → `payments` 1행만 생성 (UNIQUE 제약 확인)
- [ ] 웹훅 **중복 수신** → 상태 중복 반영 안 됨
- [ ] 웹훅 **서명 불일치** → 401, 처리 안 됨
- [ ] 결제 실패 3회 → `status = PAUSED` (구독) / 미수금 등록 (건별)

### 3.5 권한 — 통합 테스트 (보안)

**이게 뚫리면 개인정보 유출 사고다.** 역할별로 남의 리소스에 접근해 본다.

- [ ] 고객 A의 토큰으로 고객 B의 주문 `GET` → **404** (403이 아니라 404. 존재 여부도 숨긴다)
- [ ] 기사가 **자기 배차가 아닌** assignment 상태 변경 → 403
- [ ] 공장이 **다른 공장의** job 조회 → 404
- [ ] `STAFF` 관리자가 환불·회원삭제 시도 → 403 (`SUPER_ADMIN` 전용)
- [ ] 만료 토큰 / 위조 서명 → 401
- [ ] refresh 토큰 **재사용 탐지** → 해당 사용자 전체 세션 무효화
- [ ] 고객 URL(`/admin/...`)에 고객 토큰으로 접근 → 미들웨어에서 차단

### 3.6 권역·슬롯 계산 — 단위 테스트

- [ ] 안강읍(3권역, 화·목)에 **수요일 조회 → 빈 슬롯 + `nextOperatingDate` = 목요일**
- [ ] 1권역은 월~토 전부 열림, 일요일은 닫힘
- [ ] 휴무일(공휴일) 등록 시 해당 날짜 제외
- [ ] **화요일 수거 + 이불(4일) → 배송일이 다음 주 화요일** (문서 09 §1.2의 그 케이스)
- [ ] 품목 여러 개 → **가장 긴 소요일** 기준
- [ ] 서비스 불가 지역 → `AREA_NOT_SERVICED` 422

### 3.7 슬롯 정원 동시성 — 통합 테스트

- [ ] 정원 5인 슬롯에 **동시 10건 주문** → 정확히 5건 성공, 5건 `SLOT_FULL` 409
  (`Promise.all`로 동시 요청, DB 제약 또는 `SELECT ... FOR UPDATE`로 방어)
- [ ] 주문 취소 시 정원 **복구됨**

### 3.8 낙관적 잠금

- [ ] 같은 assignment에 **동시 2회 complete** → 1건 성공, 1건 409 `ORDER_VERSION_CONFLICT`
- [ ] 기사와 관리자가 동시에 상태 변경 → 나중 요청 409

## 4. E2E 시나리오 (Playwright) — 4개만

시간이 많이 드는 계층이라 **핵심 흐름 4개**로 제한한다.

| # | 시나리오 | 커버 범위 |
|---|---|---|
| E2E-1 | **행복 경로 전체**: 가입 → 주소등록 → 수거신청 → 배차 → 기사수거 → 공장검수(금액동일) → 세탁 → 배송 → 결제완료 | 4개 역할 전부 |
| E2E-2 | **추가금 승인 경로**: 검수에서 수량 증가 → 고객 승인 → 진행 | 문서 06의 핵심 분기 |
| E2E-3 | **구독 경로**: 구독 가입 → 주문 → 커버 → 잔여횟수 차감 확인 | 결제·구독 |
| E2E-4 | **예외 경로**: 수거 부재 → 재배차 → 정상 완료 | 실패 복구 |

각 시나리오는 **역할별로 브라우저 컨텍스트를 분리**해 실행한다(고객/기사/공장/관리자 동시).

## 5. 수동 테스트 체크리스트 (자동화 못 하는 것)

파일럿 운영(Phase 6) 전에 **실제 기기로** 확인한다.

### 기사 앱 — 현장 조건
- [ ] **야외 직사광선**에서 화면이 보이는가
- [ ] **장갑 낀 손**으로 버튼이 눌리는가
- [ ] 지하주차장 등 **음영지역**에서 상태 변경 시 어떻게 되는가 (에러 메시지가 명확한가)
- [ ] 카메라 촬영 → 업로드가 **LTE에서 몇 초** 걸리는가 (10초 넘으면 리사이즈 강화)
- [ ] **배터리** — 3시간 슬롯 동안 앱 켜두면 몇 % 소모되는가
- [ ] 한 손 조작으로 배차 목록 → 출발 → 완료까지 가능한가

### PWA — 플랫폼별
- [ ] **iOS Safari**: 홈화면 추가 → 푸시 수신 (16.4 미만 기기에서는 안 온다는 것 확인)
- [ ] iOS 홈화면 추가 **안 한** 상태 → 알림톡은 정상 수신되는가
- [ ] Android Chrome: 설치 배너, 푸시
- [ ] 오프라인에서 앱 실행 → 캐시된 화면 표시 + 명확한 오프라인 안내

### 결제 (테스트 환경)
- [ ] 카드 등록 → 빌링키 발급
- [ ] 자동 결제 성공/실패
- [ ] 부분 환불 후 영수증 금액
- [ ] **한도 초과 카드**로 실패 시나리오

## 6. CI 게이트

```yaml
# PR → main
1. lint (eslint) + typecheck (tsc --noEmit)     ← 실패 시 머지 불가
2. 단위 테스트 (Vitest)                          ← 실패 시 머지 불가
3. 통합 테스트 (Testcontainers)                  ← 실패 시 머지 불가
4. 빌드 (web + api)                              ← 실패 시 머지 불가
5. E2E (Playwright)                              ← main 머지 후 staging에서만 (PR에선 느려서 제외)
```

### 커버리지 목표 (강제하지 않고 참고만)
| 영역 | 목표 |
|---|---|
| `packages/shared` (상태머신·금액계산) | **90% 이상** — 여기만 강제 |
| `apps/api/src/modules/order`, `billing`, `subscription` | 70% |
| 나머지 API | 40% |
| 프론트 | 측정만, 목표 없음 |

> 전체 커버리지 목표를 세우면 의미 없는 CRUD 테스트를 쓰게 된다. **shared만 강제**한다.

## 7. 테스트 데이터

```
apps/api/test/fixtures/
├─ users.ts        # 고객2, 기사2, 공장1, 관리자2(SUPER/STAFF)
├─ orders.ts       # 상태별 주문 1건씩 (20개 상태 전부)
├─ builders.ts     # anOrder().withStatus('WASHING').withItems(...).build()
└─ setup.ts        # 각 테스트 전 DB 트랜잭션 시작 → 후 롤백
```

**원칙**
- 테스트 간 데이터 격리는 **트랜잭션 롤백**으로 (truncate보다 빠름)
- 시드 데이터(`seed/*.json`)는 테스트에서도 그대로 로드 → 요금표 변경이 테스트에 반영됨
- 실제 고객 데이터를 테스트에 복사 금지 (개인정보)
- 날짜는 **고정값 주입** (`vi.setSystemTime`) — "오늘"에 의존하는 테스트는 언젠가 깨진다

## 8. 개발 단계별 테스트 작성 시점

| Phase | 같이 쓸 테스트 |
|---|---|
| Phase 0 | Testcontainers 셋업, fixtures 골격 |
| **Phase 1** | **상태 전이표 전수 테스트 (§3.1)** ← 여기서 안 쓰면 영원히 못 씀 |
| Phase 1 | 권한 테스트 (§3.5), 권역·슬롯 계산 (§3.6) |
| Phase 2 | 낙관적 잠금 (§3.8), 슬롯 동시성 (§3.7) |
| Phase 3 | 금액 계산 (§3.2) |
| Phase 4 | 구독 차감 (§3.3), 결제 멱등성 (§3.4) |
| Phase 5 | E2E 4개 (§4) |
| Phase 6 | 수동 체크리스트 (§5), k6 부하 |

> **Phase 1의 상태머신 테스트만큼은 미루지 말 것.** 이후 모든 기능이 상태머신 위에 얹히는데,
> 테스트 없이 계속 얹으면 나중에 손을 못 댄다.
