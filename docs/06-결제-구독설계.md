# 06. 결제 · 구독 설계

> 이 서비스의 결제는 일반 쇼핑몰과 **근본적으로 다르다.**
> **주문 시점에는 최종 금액을 알 수 없다.** (실제 세탁물 수량·품목은 공장 검수 후 확정)
> 따라서 "결제 후 배송"이 아니라 **"수거 → 검수 → 금액 확정 → 청구"** 구조로 설계한다.

---

## 1. 결제 시점 전략 비교

| 방식 | 설명 | 판정 |
|---|---|---|
| ① 주문 시 선결제 | 예상 금액으로 먼저 결제 | ❌ 차액 발생 시 추가결제/부분환불이 매번 필요 → 운영 지옥 |
| ② 주문 시 가승인(선승인) | 예상액 + 여유분 한도만 잡고 검수 후 실제 금액 확정 | ⚠️ 국내 PG 부분취소로 흉내는 되지만 고객 한도가 묶여 CS 발생 |
| ③ **검수 후 청구 (채택)** | 카드(빌링키)만 미리 등록 → 검수 확정 후 자동 결제 | ✅ 세탁 업계 표준. 고객 부담 없음 |

**채택: ③ 빌링키 기반 후청구**
- 가입/첫 주문 시 카드 등록만 (billingKey 발급, 실제 승인 없음)
- 검수 완료 → 금액 확정 → 고객 승인(필요 시) → 배송 완료 시점에 자동 결제
- 결제 실패해도 세탁물은 이미 전달됨 → 미수금 관리 필요 (아래 5절)

---

## 2. 금액 계산 파이프라인

```
① 주문 신청 시 (estimated_amount)
   Σ (품목 단가 × 고객 입력 예상 수량)
        ↓
② 공장 검수 후 (final_amount)
   Σ (품목 단가_스냅샷 × 확정 수량) + 검수 중 추가된 품목
        ↓
③ 구독 커버액 계산  ※ 여기서는 계산만. 횟수 차감은 아직 하지 않는다
   구독 ACTIVE + (remaining_count - 예약중인 건수) > 0 이면
     subscription_covered_amount = MIN(final_amount, plan.included_amount_per_use)
   아니면 0
   ※ restricted_item_codes 가 있는 플랜(셔츠정기권 등)은 해당 품목 금액만 커버
        ↓
④ 할인 적용
   discount_amount = 구독회원 초과분 할인(extra_discount_rate)
                     [ + 쿠폰 + 포인트 ]  ← 2차 기능. MVP에서는 0
        ↓
⑤ 최종 청구액
   payable_amount = final_amount - subscription_covered_amount - discount_amount
   (0원이면 결제 스킵, 바로 COMPLETED)
```

### 계산 예시
```
플랜: STANDARD_M 스탠다드 (월 39,900원 / 월 4회 / 회당 15,000원까지 포함 / 초과분 10% 할인)

주문 A) 검수 확정 12,000원
  → 구독 커버 12,000 / 초과 0 / 청구액 0원, 잔여횟수 4→3

주문 B) 검수 확정 28,000원
  → 구독 커버 15,000 / 초과 13,000 → 10% 할인 → 11,700
  → 청구액 11,700원, 잔여횟수 3→2

주문 C) 잔여횟수 0인 상태, 확정 20,000원
  → 구독 커버 0 / 구독회원 할인 10% → 청구액 18,000원
```

### ⚠️ 구독 횟수 차감 시점 — 3단계로 분리한다

혼동하기 쉬운 부분이라 명확히 한다. **`remaining_count`는 `COMPLETED` 시점에만 줄어든다.**

| 시점 | 하는 일 | `remaining_count` |
|---|---|---|
| 주문 신청 (`REQUESTED`) | **예약(hold)** — 진행중 주문 수만 세어 화면에 "2회 남음(1건 사용 예정)" 표시 | **변화 없음** |
| 검수 확정 (`INSPECTED`) | 커버 금액 **계산만** 해서 `subscription_covered_amount`에 기록 | **변화 없음** |
| 거래 완료 (`COMPLETED`) | **확정 차감** `remaining_count -= 1` | **−1** |

신청 시점에 차감하면 취소·수거실패·검수 후 반송마다 복구 로직이 필요하고,
그중 하나만 빠져도 고객 횟수가 새어나간다. 실무에서 가장 흔한 버그 지점이다.

> **잔여 횟수 판정식:** `가용 횟수 = remaining_count − (진행중이면서 구독 적용된 주문 수)`
> 고객 화면과 견적 API 모두 이 식을 쓴다.

## 3. 카드 등록 (빌링키) 흐름 — 토스페이먼츠 기준

```
[고객 앱]                    [우리 API]                  [토스페이먼츠]
   │ 카드 등록하기 클릭          │                              │
   ├─ POST /billing/cards/register-request ──▶                 │
   │ ◀── { clientKey, customerKey }                            │
   │                                                            │
   ├─ 토스 결제위젯 SDK 실행 (카드번호는 토스가 직접 수집) ──────▶│
   │ ◀────────────────── successUrl?authKey=xxx ────────────────┤
   │                             │                              │
   ├─ POST /billing/cards/confirm { authKey, customerKey } ─▶   │
   │                             ├─ POST /v1/billing/authorizations/issue ─▶
   │                             │ ◀── { billingKey, card: {company, number(마스킹)} }
   │                             ├─ billing_keys 테이블에 암호화 저장
   │ ◀── { cardId, "신한 ****1234" }                            │
```

**절대 원칙**
- 카드번호 전체 / CVC / 유효기간은 **우리 서버를 거치지도, 저장하지도 않는다** (PCI-DSS)
- `billingKey`는 AES-256-GCM 암호화 후 저장, 키는 환경변수/KMS
- 표시용으로는 `card_company` + `card_last4` 만 사용

## 4. 자동 결제 실행

### 4.1 건별 주문 결제
```
주문 DELIVERED 상태 진입
        ↓
BullMQ 큐에 결제 잡 등록 (지연 0초)
        ↓
payable_amount == 0  →  결제 스킵, COMPLETED
payable_amount > 0   →  토스 billingKey 결제 요청
        │                Idempotency-Key = payment.id (중복 승인 방지)
        ├─ 성공 → payments.status=PAID, 주문 COMPLETED, 영수증 알림톡
        └─ 실패 → payments.status=FAILED, 주문은 DELIVERED 유지
                  → 재시도 큐 (1시간 후, 24시간 후, 72시간 후 총 3회)
                  → 3회 모두 실패 시 관리자 미수금 목록에 등록 + 고객 알림톡
```

### 4.2 구독 정기 결제
```
매일 03:00 Cron
        ↓
SELECT * FROM subscriptions
WHERE status IN ('ACTIVE','PAST_DUE') AND next_billing_at <= now()
        ↓
각 건 결제 요청 (Idempotency-Key = subscriptionId + billingPeriod)
        │
        ├─ 성공 → next_billing_at += 1개월
        │         remaining_count = plan.included_count  (횟수 리셋)
        │         retry_count = 0, status = ACTIVE
        │
        └─ 실패 → retry_count++, status = PAST_DUE
                  retry_count < 3  → next_billing_at = +1일 (재시도)
                  retry_count >= 3 → status = PAUSED, 고객·관리자 알림
                                     (구독 혜택 중지, 이후 주문은 일반요금)
```

### 4.3 멱등성 (중복 결제 방지) — 필수
```
payments.idempotency_key UNIQUE
  건별   : "order:{orderId}:{attempt}"
  구독   : "sub:{subscriptionId}:{YYYY-MM}"
```
같은 키로 다시 들어오면 새 승인을 보내지 않고 기존 `payments` 레코드를 반환한다.
큐 재실행·웹훅 중복·사용자 더블클릭 전부 여기서 막힌다.

## 5. 결제 실패 · 미수금 처리

| 상황 | 처리 |
|---|---|
| 배송 완료 후 결제 실패 | 세탁물은 이미 전달됨 → 주문 `DELIVERED` 유지, 미수금 등록 |
| 미수금 존재 고객 | 신규 주문 시 **경고 표시**, 미수금 2건 이상이면 신규 주문 차단 |
| 카드 만료/한도 초과 | 고객에게 "카드 정보 갱신" 알림톡 + 앱 내 배너 |
| 3회 재시도 실패 | 관리자 미수금 목록 → 전화 안내 → 계좌이체 수동 처리(`method=TRANSFER`) |

> 실무상 **결제 실패는 반드시 발생한다.** 관리자 화면에 "미수금" 메뉴를 1차부터 넣는다.

## 6. 환불 정책 · 처리

| 사유 | 환불 범위 |
|---|---|
| 수거 전 취소 | 결제 이전이므로 환불 없음 (구독 횟수도 미차감) |
| 수거 후 고객 변심 | 원상 반송 + 수거/배송비만 청구 (정책 결정 필요) |
| 세탁 불가 반송 | 전액 미청구 |
| 세탁 품질 불만 | 재세탁 우선, 불가 시 해당 품목 금액 환불 |
| 손상 | 해당 품목 금액 + 배상 (`issues.compensation_amount`) |
| 분실 | 세탁업 표준약관 배상 기준 적용 (구입가 × 배상비율) |

```
POST /admin/payments/:id/refund { amount, reason }
        ↓
토스 결제취소 API (부분취소 지원)
        ↓
refunds 레코드 생성 → payments.status = PARTIAL_REFUNDED / REFUNDED
        ↓
고객 알림톡 + 감사로그
```
