# 11. 비기능 요구사항 (NFR) · 보안 · 개인정보 정책

> 이 문서의 목표치는 **"측정 가능한 숫자"** 로 적었다. "빨라야 한다" 같은 문장은 검증할 수 없다.
> 오픈 초기 규모(일 25건)에 맞춘 값이며, 과도한 목표는 일부러 피했다.

## 1. 성능 목표

### API 응답시간 (서버 처리 시간 기준, p95)

| 구분 | 대상 | 목표 |
|---|---|---|
| 조회 (단건) | 주문 상세, 배차 상세 | **≤ 300ms** |
| 조회 (목록) | 주문 목록, 배차 목록 | **≤ 500ms** |
| 조회 (관리자 검색) | 전체 주문 검색 | **≤ 1s** |
| 쓰기 | 주문 생성, 상태 변경 | **≤ 800ms** |
| 외부 연동 포함 | 결제 승인 | **≤ 5s** (PG 응답 대기 포함) |
| 파일 | 사진 업로드 (presign 발급) | **≤ 200ms** |

### 프론트엔드 (모바일 4G 기준)

| 지표 | 목표 | 비고 |
|---|---|---|
| LCP (최대 콘텐츠 표시) | **≤ 2.5s** | 고객 홈, 기사 배차 목록 |
| INP (상호작용 응답) | **≤ 200ms** | 기사 버튼 탭 |
| CLS (레이아웃 이동) | **≤ 0.1** | |
| 초기 번들 (gzip) | **≤ 250KB** | 역할별 코드 스플리팅 필수 |
| 사진 업로드 완료 | **≤ 10s / 장** | LTE 기준. 초과 시 리사이즈 강화 |

> **기사 화면의 INP가 가장 중요하다.** 하루 25번 누르는 버튼이 반응이 느리면 기사가 앱을 안 쓴다.

### 부분 장애 시 우선순위
장애가 나도 **세탁물은 물리적으로 계속 움직인다.** 그래서 기능별 중요도를 나눈다.

| 등급 | 기능 | 죽으면 |
|---|---|---|
| **필수** | 기사 배차 조회 · 상태 변경 | 현장이 멈춘다. 최우선 복구 |
| **필수** | 공장 검수 입력 | 세탁 진행 불가 |
| 중요 | 고객 주문 신청 | 신규 매출 중단 (기존 건은 진행) |
| 보통 | 결제 | **큐에 쌓았다가 나중에 처리 가능** |
| 낮음 | 알림, 통계, 리뷰 | 지연돼도 무방 |

## 4. 개인정보 — 필드별 암호화 정책 ⭐

### 4.1 왜 "전부 암호화"를 하지 않는가

처음 설계에서 주소·연락처를 전부 암호화했는데, **그러면 관리자가 주소로 주문을 검색할 수 없다.**
AES-GCM은 같은 값도 매번 다른 암호문이 되므로 `LIKE '%테헤란로%'` 가 불가능하다.
"강남구 어제 주문 좀 찾아줘" 같은 일상적인 CS 대응이 막힌다.

법적으로도 **주소·전화번호는 암호화 의무 대상이 아니다.**
「개인정보의 안전성 확보조치 기준」상 저장 시 암호화 의무는 **고유식별정보(주민등록번호 등),
비밀번호, 생체인식정보**에 대한 것이고, 우리는 이 중 어느 것도 수집하지 않는다.

> ⚠️ **법령 해석은 최종적으로 확인이 필요하다.** 위 내용은 일반적인 실무 기준이며,
> 통신판매업 신고·개인정보처리방침 작성 시 관련 기관 안내나 법률 자문으로 검증할 것.
> 아래 정책은 "의무는 아니지만 유출 피해가 큰 필드는 암호화한다"는 **자체 기준**이다.

### 4.2 필드별 처리 방침

| 필드 | 처리 | 이유 |
|---|---|---|
| `users.phone` | **암호화** (AES-256-GCM) | 유출 시 스팸·피싱 표적. 검색은 아래 두 컬럼으로 |
| `users.phone_hash` | HMAC-SHA256 + pepper, **UNIQUE** | 로그인·중복검사 (완전일치만 필요) |
| `users.phone_last4` | **평문**, 인덱스 | 관리자 검색("1234"), 기사 화면 표시("010-****-1234") |
| `users.name` | 평문 | 검색 필수. 이름만으로는 식별력 낮음 |
| `addresses.road_address` | **평문**, 인덱스 | **관리자·기사 검색에 필수.** 도로명까지는 건물 단위 |
| `addresses.detail_address` | **암호화** | 동/호수 — 여기부터 개인 특정 가능 |
| `addresses.entrance_note` | **암호화** | **공동현관 비번 포함. 유출 시 피해 최대** |
| `addresses.lat/lng` | 평문 | 배차 거리 계산에 필수 |
| `payments.*` | 카드정보 **저장 안 함** | PG가 보관. 우리는 billingKey만 (암호화) |
| `billing_keys.billing_key` | **암호화** | 유출 시 무단 결제 가능 |
| 사진 | S3 **비공개 버킷** + presigned URL (5분) | 직접 URL 노출 금지 |

### 4.3 암호화 외의 방어선 (평문 필드를 지키는 방법)

평문으로 두는 대신 아래를 **반드시** 구현한다.

- [ ] **저장장치 암호화(TDE / 디스크 암호화)** — 클라우드 DB는 기본 제공, 켜져 있는지 확인
- [ ] **DB 계정 분리** — 애플리케이션 계정은 필요한 테이블만 접근
- [ ] **관리자 개인정보 조회 감사로그** — `audit_logs.action = 'CUSTOMER_PII_VIEW'` (문서 03)
- [ ] **관리자 목록 화면에서는 마스킹** — 상세 화면 진입 시에만 전체 표시 + 로그 기록
  - 이름 `최*민` / 전화 `010-****-1234` / 주소 `경주시 황성동 ***`
- [ ] **대량 조회 차단** — 관리자 검색 결과 100건 초과 시 다운로드 불가, 500건 초과 시 알림
- [ ] 개인정보 포함 응답은 **로그에 남기지 않음** (Pino redact 설정)

## 5. 계정 · 인증 정책

### 5.1 고객 (SMS 인증)

| 항목 | 정책 |
|---|---|
| 인증번호 | 6자리 숫자, **5분** 유효 |
| 발송 제한 | 동일 번호 **분당 1회 / 일 5회** |
| 검증 실패 | **5회 실패 시 해당 인증번호 폐기**, 재발송 필요 |
| 발송 남용 방지 | 동일 IP 시간당 20회 초과 시 차단 |

### 5.2 기사 · 공장 · 관리자 (비밀번호)

| 항목 | 정책 |
|---|---|
| 해싱 | **Argon2id** (memory 19MB, iterations 2, parallelism 1) |
| 최소 길이 | **10자 이상** |
| 구성 | 영문 + 숫자 필수, 특수문자 권장 (강제하지 않음) |
| 금지 | 아이디 포함, 연속 4자 이상(`1234`, `abcd`), 흔한 비밀번호 목록 |
| 변경 주기 | **강제하지 않음** (주기적 변경 강제는 오히려 약한 비밀번호를 유발) |
| **계정 잠금** | **5회 연속 실패 → 15분 잠금** (`failed_login_count`, `locked_until`) |
| 잠금 해제 | 15분 경과 자동 해제, 또는 관리자 수동 해제 |
| 초기 비밀번호 | 관리자가 생성 시 임시 발급 → **최초 로그인 시 변경 강제** |
| 2FA | 관리자 계정만, **2차 기능** (TOTP) |

### 5.3 세션 · 토큰

| 항목 | 정책 |
|---|---|
| Access Token | JWT **15분**, 메모리 보관 (localStorage 금지) |
| Refresh Token | **14일**, httpOnly + Secure + SameSite=Lax 쿠키 |
| 토큰 회전 | refresh 사용 시마다 재발급, 이전 토큰 무효화 |
| **재사용 탐지** | 폐기된 refresh 재사용 감지 → **해당 사용자 전체 세션 강제 로그아웃** + 알림 |
| 동시 로그인 | 고객·기사 허용 / **관리자는 1세션만** |
| 기사 예외 | 기사는 근무 중 로그아웃되면 안 됨 → refresh **30일** |
| 로그아웃 | refresh 즉시 폐기 (DB에서 삭제) |

### 5.4 Rate Limiting

| 대상 | 제한 |
|---|---|
| 인증 API (`/auth/*`) | IP당 **분당 5회** |
| 일반 API | 사용자당 **분당 60회** |
| 관리자 검색 | 사용자당 **분당 30회** |
| 파일 업로드 presign | 사용자당 **분당 20회** |
| 웹훅 | 제한 없음 (서명 검증으로 방어) |

## 7. 데이터 보존 · 파기 정책

### 7.1 법정 보존 의무 (전자상거래법 시행령)

| 항목 | 보존 기간 |
|---|---|
| 계약 또는 청약철회 등에 관한 기록 | **5년** |
| 대금결제 및 재화 등의 공급에 관한 기록 | **5년** |
| 소비자의 불만 또는 분쟁처리에 관한 기록 | **3년** |
| 표시·광고에 관한 기록 | 6개월 |

> ⚠️ 위 기간은 일반적인 전자상거래 기준이다. **개인정보처리방침 작성 시 최종 확인 필요.**

### 7.2 우리 정책

| 데이터 | 보존 | 파기 방법 |
|---|---|---|
| 주문·결제 기록 | **5년** | 5년 후 배치 삭제 |
| 클레임(`issues`) | **3년** | |
| 회원 개인정보 (이름·전화·주소) | **탈퇴 즉시 파기** | 비식별 값으로 덮어쓰기 (`탈퇴회원`, `00000000000`) |
| 사진 (`order_photos`) | **90일** | 자동 삭제 배치. 단 `issues` 연결 건은 **분쟁 종료까지 보존** |
| 알림 발송 이력 | 1년 | |
| 감사로그(`audit_logs`) | **3년** | 삭제 금지 대상 |
| 애플리케이션 로그 | 90일 | |
| DB 백업 | 30일 | |

### 7.3 탈퇴 처리 순서

```
① 고객이 탈퇴 요청
        ↓
② 진행 중 주문 있으면 차단 ("배송 완료 후 탈퇴 가능")
③ 미수금 있으면 차단
        ↓
④ users.status = WITHDRAWN, withdrawn_at = now()
⑤ 개인정보 필드 즉시 덮어쓰기
     name → '탈퇴회원', phone/phone_hash/phone_last4 → 랜덤 더미
     email → NULL, addresses 전체 → 삭제
⑥ billing_keys → PG에 삭제 요청 + 로컬 삭제
        ↓
⑦ orders / payments 는 customer_id만 남기고 유지 (5년)
   → 통계·정산에는 쓰이지만 개인은 식별 불가
```

> **핵심:** "탈퇴 30일 후 전부 삭제"는 **법정 보존 의무와 충돌**한다.
> 개인정보는 즉시 파기하되 거래기록은 남긴다.
