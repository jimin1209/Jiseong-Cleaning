# 12. 운영 런북 (장애 대응 · 백업 · 배포)

> **전제: 온콜은 사실상 1명(최지민)이다.** 24시간 즉시 대응은 불가능하다.
> 그래서 이 런북의 핵심은 "빨리 고치는 법"이 아니라
> **"앱이 죽어도 세탁물은 계속 돌게 하는 법"** 이다.

---

## 0. 가장 중요한 원칙 — 오프라인 백업 운영

세탁물은 물리적으로 이미 고객 집에, 기사 차에, 공장에 있다.
**앱이 죽어도 그 세탁물은 오늘 배송돼야 한다.**

### 앱이 완전히 죽었을 때 (P1)

```
① 관리자가 기사·공장에 전화/카톡으로 즉시 통보
     "앱 장애. 지금부터 수기 운영합니다"
② 기사는 종이 배차표로 운행 (아래 §0.1)
③ 공장은 종이 검수표로 작업 (아래 §0.2)
④ 고객 알림은 관리자가 카톡·전화로 개별 안내
⑤ 복구 후 관리자가 종이 기록을 앱에 일괄 입력
```

### 0.1 상시 준비물 — 기사

- [ ] **당일 배차표 종이 출력본**을 매일 아침 기사에게 전달 (또는 카톡 이미지)
  - 관리자 화면 A-05에 **"배차표 인쇄"** 버튼을 넣는다 ← Phase 2 구현 항목
- [ ] 기사 휴대폰에 관리자 전화번호 등록
- [ ] 수기 기록 양식: 주문번호 / 수거·배송 / 시각 / 봉투수 / 특이사항

### 0.2 상시 준비물 — 공장

- [ ] 종이 검수표 (주문번호, 품목, 수량, 특이사항 칸)
- [ ] 세탁물 태그에 **주문번호를 물리적으로 부착** (QR 라벨 프린터)
  → 앱이 죽어도 어느 세탁물이 누구 것인지 알 수 있다. **이게 없으면 복구 불가능한 사고가 난다**

> ⚠️ **QR 라벨 부착은 시스템 장애 대비의 핵심이다.** Phase 3 필수 구현.

## 1. 장애 등급

| 등급 | 정의 | 목표 대응 착수 | 예시 |
|---|---|---|---|
| **P1** | 서비스 전체 중단, 또는 금전 사고 | **30분 이내** (주간) / 아침 확인 (심야) | 서버 다운, DB 다운, 이중 결제 |
| **P2** | 일부 기능 장애, 우회 가능 | **당일 내** | 알림 미발송, 사진 업로드 실패, 특정 화면 오류 |
| **P3** | 불편하지만 운영 가능 | **1주 이내** | 통계 오류, UI 깨짐, 오타 |

**심야(22:00~08:00) 정책:** P1이라도 즉시 대응하지 않는다. 이 시간엔 수거·배송이 없다.
단 **결제 관련 P1은 예외** — 이중 결제·과금 오류는 확인 즉시 결제 큐를 중단시킨다.

## 2. 장애 대응 절차 (공통)

```
① 확인      Sentry / 알람 / 사용자 제보 → 재현 시도
② 등급 판정  P1 / P2 / P3
③ 통보      P1이면 기사·공장에 즉시 통보 (§0)
④ 지혈      원인 규명보다 서비스 복구 우선
              - 최근 배포가 원인이면 → 즉시 롤백 (§5)
              - 특정 기능만 문제면 → 기능 플래그로 차단
⑤ 복구 확인  /health + 핵심 시나리오 1건 수동 확인
⑥ 기록      장애 로그에 시각·증상·원인·조치 기록
⑦ 사후      P1은 반드시 재발방지책 1개 이상 도출
```

**원칙: 지혈이 진단보다 먼저다.** 원인을 몰라도 롤백으로 서비스가 돌아오면 그게 우선이다.

## 3. 시나리오별 런북

### 3.1 🔴 API 서버 응답 없음 (P1)

**증상:** `/health` 실패, 전 사용자 접속 불가

```
1. 상태 확인
   curl https://api.../health
   호스팅 대시보드에서 인스턴스 상태·재시작 이력 확인

2. 즉시 조치 (순서대로 시도)
   a) 인스턴스 재시작
   b) 최근 24시간 내 배포가 있었나 → 있으면 롤백 (§5)
   c) DB 연결 확인 (§3.2로 이동)
   d) 메모리/CPU 확인 → OOM이면 인스턴스 사양 상향

3. 통보 (§0) — 5분 안에 복구 안 되면 즉시
4. 복구 후: 배차 목록 1건 조회로 확인
```

**흔한 원인:** 배포 직후 환경변수 누락 / DB 커넥션 풀 고갈 / 메모리 누수

---

### 3.2 🔴 DB 접속 불가 (P1)

```
1. 호스팅(Neon/Railway 등) 상태 페이지 확인 → 벤더 장애면 대기 + 통보
2. 커넥션 수 확인
   SELECT count(*), state FROM pg_stat_activity GROUP BY state;
   → 'idle in transaction' 다수면 커넥션 누수. API 재시작으로 해소
3. 디스크 full 확인 → 로그·오래된 사진 정리
4. 벤더 장애가 장기화되면 → 백업에서 복구 (§6.3)
```

> **커넥션 풀은 반드시 상한을 건다** (`connection_limit=10`). 무제한이면 API가
> DB를 죽인다. Prisma `DATABASE_URL`에 파라미터로 지정.

---

### 3.3 🔴 결제 이중 승인 / 과금 오류 (P1 — 최우선)

**금전 사고이므로 다른 어떤 장애보다 먼저 처리한다.**

```
1. 즉시 결제 큐 중단
   BullMQ payment 큐 pause → 추가 피해 차단

2. 피해 범위 확인
   SELECT order_id, count(*) FROM payments
   WHERE status='PAID' AND approved_at > now() - interval '24 hours'
   GROUP BY order_id HAVING count(*) > 1;

3. 중복 건 즉시 환불 (PG 취소 API) + refunds 기록

4. 고객에게 선제 안내
   "중복 결제가 확인되어 즉시 환불 처리했습니다" — 고객이 발견하기 전에 알린다

5. 원인 규명: idempotency_key 누락? UNIQUE 제약 없음? 웹훅 중복 처리?
6. 수정 배포 후 큐 재개
```

> **선제 안내가 핵심이다.** 고객이 먼저 발견하면 신뢰가 무너지고 분쟁으로 간다.

---

### 3.4 🟠 PG(토스페이먼츠) 장애 (P1)

```
1. 토스페이먼츠 상태 페이지 / 공지 확인
2. 결제 큐를 중단하지 말고 "재시도 대기"로 전환
   → 주문은 DELIVERED 상태로 유지, 결제만 지연
3. 고객 안내: "결제는 나중에 자동 처리됩니다" (서비스는 정상 진행)
4. PG 복구 후 큐 재개 → 밀린 결제 순차 처리
```

**핵심:** PG가 죽어도 **수거·세탁·배송은 계속한다.** 결제는 나중에 해도 된다.
문서 11 §2의 기능 등급표에서 결제가 "보통"인 이유다.

---

### 3.5 🟠 기사가 상태 변경을 못 함 (P1 — 현장 마비)

```
1. 기사에게 확인: 특정 화면만? 전체? 특정 기사만? 통신 상태?
2. 전체 장애면 → §3.1
3. 특정 건만이면
   - 낙관적 잠금 충돌(409)? → 앱 새로고침 후 재시도 안내
   - 상태가 이미 넘어가 있나? → 관리자 화면에서 확인
4. 우회: 기사가 관리자에게 전화 → 관리자가 대신 상태 변경
   (관리자 강제 전이 A-04, 사유에 "기사 앱 장애 대리 입력" 기록)
5. 최후: 종이 배차표 운영 (§0.1)
```

> 관리자 강제 전이 기능이 **현장 장애의 유일한 우회로**다. Phase 1 필수인 이유.

---

### 3.6 🟠 사진 업로드 실패 (P2)

```
1. S3/스토리지 상태 확인, presigned URL 만료(5분) 여부 확인
2. 기사에게 임시 안내:
   "사진은 휴대폰 갤러리에 저장해 두시고, 상태 변경만 진행하세요"
   → 사진 필수 검증을 관리자가 임시로 우회 처리
3. 복구 후 기사에게 사진 일괄 업로드 요청 (관리자 화면에서 사후 첨부)
```

> ⚠️ 사진은 **분쟁 시 유일한 증거**다. 임시 우회한 건은 목록으로 남겨 반드시 사후 보완한다.

---

### 3.7 🟡 알림톡 / 푸시 미발송 (P2)

```
1. 발송 이력 확인: SELECT * FROM notifications WHERE status='FAILED' ...
2. 원인별
   - 알림톡 템플릿 반려/변경 → 재승인 필요 (수일 소요) → 임시로 SMS 폴백
   - 발신프로필 잔액 부족 → 충전
   - FCM 토큰 만료 → 자동 정리 배치
3. 긴급 건(추가금 승인 대기)은 관리자가 직접 전화
```

---

### 3.8 🟠 슬롯 정원 초과 예약 (P2)

```
1. 해당 날짜·슬롯의 실제 주문 수 확인
2. 초과분을 다른 슬롯으로 재배정 → 고객에게 개별 연락·양해
3. 원인: 동시성 방어 실패 → 문서 10 §3.7 테스트 추가
4. 임시 조치: 해당 슬롯 capacity를 실제 수용량까지 낮춤
```

---

### 3.9 🔴 개인정보 유출 의심 (P1 — 법적 대응 필요)

```
1. 즉시 차단: 의심 계정 정지, 관련 토큰 전량 무효화, 필요시 서비스 일시 중단
2. 범위 파악: audit_logs에서 대량 조회·다운로드 이력 확인
      SELECT * FROM audit_logs WHERE action LIKE '%PII%'
        AND created_at > ? ORDER BY created_at;
3. 증거 보전: 로그·DB 스냅샷 별도 보관 (덮어쓰기 금지)
4. ⚠️ 법정 통지·신고 의무 확인 — 정보주체 통지 및 관계기관 신고 기한이 정해져 있다.
   기한과 요건은 개인정보보호법 규정을 반드시 확인하고, 필요시 법률 자문을 받는다.
5. 재발 방지: 접근 권한 재점검, 대량 조회 차단 임계치 하향
```

> **이 항목만은 혼자 판단하지 말 것.** 신고 기한·범위 판단을 잘못하면 과태료 대상이다.

## 5. 배포 · 롤백

### 배포 절차
```
1. main 머지 → staging 자동 배포
2. staging에서 E2E 4개 통과 확인 (문서 10 §4)
3. 태그 생성 → production 배포 (수동 승인)
4. 배포 후 5분간 관찰: Sentry 에러율, /health, 핵심 API 응답
5. 이상 시 즉시 롤백
```

**배포 시간대 규칙**
- ✅ **화~목 오후 2~4시** — 문제가 생겨도 저녁 피크 전에 고칠 수 있다
- ❌ **금요일 오후 / 저녁 6시 이후 / 주말** — 문제 생기면 대응 못 한다
- ❌ 수거·배송 피크(18~21시) 중 배포 금지

### 롤백
```
애플리케이션:  이전 태그 재배포 (Vercel/Railway는 대시보드에서 1클릭)
DB 마이그레이션: ⚠️ 자동 롤백 불가

  원칙: 마이그레이션은 항상 "하위 호환"으로 작성한다
    - 컬럼 추가 O / 컬럼 삭제·이름변경은 2단계로 분리
      1차 배포: 새 컬럼 추가 + 양쪽 쓰기
      2차 배포(며칠 후): 구 컬럼 읽기 중단
      3차 배포: 구 컬럼 삭제
    - 이렇게 하면 앱만 롤백해도 DB는 그대로 동작한다
```

## 6. 백업 · 복구

### 6.1 백업 정책

| 대상 | 주기 | 보존 | 위치 |
|---|---|---|---|
| PostgreSQL 자동 백업 | 호스팅 기본 (일 1회 + PITR) | 7~30일 | 벤더 |
| **PostgreSQL 수동 덤프** | **매일 03:00 `pg_dump`** | **30일** | **별도 스토리지(다른 벤더)** |
| 사진 (S3) | 버전 관리 활성화 | 30일 | 동일 버킷 |
| 환경변수·시크릿 | 변경 시마다 | — | 오프라인 암호화 보관 |
| 시드·설정 JSON | Git | 영구 | 저장소 |

> ⚠️ **벤더 백업만 믿지 않는다.** 호스팅 계정 자체에 문제가 생기면(결제 실패, 계정 정지)
> 백업도 같이 못 쓴다. **반드시 다른 곳에 사본을 둔다.**

### 6.2 RPO / RTO
- **RPO 1시간** — 최악의 경우 1시간치 데이터 유실 감수 (PITR 사용 시 훨씬 짧음)
- **RTO 4시간** — 완전 복구까지 목표 시간

### 6.3 복구 리허설 (분기 1회, 필수)

**백업은 복구해 본 적이 있어야 백업이다.**

```
1. 최신 덤프를 임시 DB 인스턴스에 복원
     pg_restore -d jiseong_restore_test latest.dump
2. 검증
   - 주문 건수가 백업 시점과 일치하는가
   - 최근 주문 1건의 상태 이력이 온전한가
   - 암호화 필드가 현재 키로 복호화되는가  ← 자주 놓치는 부분
3. 소요 시간 측정 → RTO 4시간 안에 되는가
4. 임시 인스턴스 삭제
5. 결과 기록 (실패했으면 그게 가장 중요한 발견이다)
```

> **암호화 키를 백업과 함께 보관하지 않으면 복구해도 주소를 읽을 수 없다.**
> 키는 백업과 **분리된 곳**에 보관하되, 분실하면 안 된다.

## 7. 연락처 · 에스컬레이션

| 대상 | 용도 | 비고 |
|---|---|---|
| 기사 | 현장 장애 통보 | 전화 (카톡 아님 — 운전 중) |
| 세탁공장 | 작업 중단·재개 통보 | 전화 |
| 호스팅 벤더 | 인프라 장애 | 대시보드 / 지원 티켓 |
| 토스페이먼츠 | 결제 장애·정산 문의 | 가맹점 지원 |
| 카카오 알림톡 대행사 | 발송 장애 | |
| 법률 자문 | 개인정보 사고, 배상 분쟁 | **사전에 확보해 둘 것** |

> **작성 필요:** 위 표의 실제 연락처를 채운 별도 파일을 만들어 **휴대폰에도 저장**한다.
> 서버가 죽었을 때 연락처를 서버에서 찾을 수는 없다.

## 8. 장애 기록 양식

```markdown
## [YYYY-MM-DD HH:MM] 제목
- 등급: P1 / P2 / P3
- 증상:
- 영향 범위: (영향받은 주문 수 / 고객 수)
- 감지 경로: 알람 / 제보 / 직접 발견
- 조치:
- 원인:
- 재발 방지: (반드시 1개 이상, 담당·기한 명시)
- 소요 시간: 감지 ~ 복구
```

> P1은 **재발 방지책 없이 종료하지 않는다.** 그게 없으면 같은 장애가 다시 난다.
