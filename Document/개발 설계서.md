# 지성크리닝 개발 설계서

## 1. 문서 개요

### 1.1 목적

본 문서는 「지성크리닝 서비스 요구사항 명세서」를 실제 시스템으로 구현하기 위한 기술 구조, 데이터 모델, API, 상태 처리, 보안, 배포 및 테스트 방안을 정의한다.

### 1.2 개발 대상

| 시스템 | 대상 환경 | 주요 사용자 |
| --- | --- | --- |
| 고객 애플리케이션 | Android | 세탁 서비스 고객 |
| 관리자 웹 | PC 및 태블릿 웹 브라우저 | 최고 관리자, 일반 관리자 |
| 관리자 모바일 | 모바일 앱 또는 반응형 웹 | 관리자, 수거·배송 담당자 |
| 백엔드 API | 클라우드 서버 | 모든 클라이언트 |
| 관리자 배치·작업 서버 | 클라우드 서버 | 알림, 예약, 통계, 데이터 정리 작업 |

### 1.3 설계 원칙

- 고객 앱과 관리자 시스템은 하나의 백엔드 API 및 데이터베이스를 사용한다.
- 주문, 결제 및 상태 변경은 중복 요청에도 한 번만 처리되도록 설계한다.
- 핵심 업무 변경에는 작업자와 변경 이력을 남긴다.
- 결제, 문자, 푸시, 주소 및 지도 기능은 외부 서비스와 분리하여 교체 가능하게 구성한다.
- 초기에는 단일 서비스로 빠르게 개발하고, 트래픽과 조직 규모가 커지면 기능별 분리를 검토한다.
- 고객 개인정보는 업무에 필요한 최소 범위에서 수집하고 권한에 따라 노출한다.

## 2. 기술 구성 권장안

아래 구성은 초기 개발을 위한 권장안이다. 최종 기술은 개발 인력의 경험과 운영 환경을 고려하여 확정한다.

| 영역 | 권장 기술 | 비고 |
| --- | --- | --- |
| 고객 Android 앱 | Kotlin, Jetpack Compose | Android 네이티브 앱 |
| 관리자 웹 | React 또는 Next.js, TypeScript | 반응형 화면 지원 |
| 관리자 모바일 | 1차: 반응형 웹, 필요 시 Android 앱 | 초기 개발 비용 절감 |
| 백엔드 API | Spring Boot, Kotlin 또는 Java | REST API 및 배치 작업 |
| 데이터베이스 | PostgreSQL | 주문·결제의 관계형 데이터 관리 |
| 캐시·임시 데이터 | Redis | 인증, 중복 요청 방지, 단기 캐시 |
| 파일 저장소 | S3 호환 오브젝트 스토리지 | 세탁물 및 배송 증빙 사진 |
| 푸시 알림 | Firebase Cloud Messaging | Android 푸시 알림 |
| API 문서 | OpenAPI 3 | 클라이언트와 서버 간 계약 관리 |
| 컨테이너 | Docker | 개발·운영 환경 일관성 확보 |
| 모니터링 | 구조화 로그, 오류 추적, 메트릭 도구 | 제품 선정 필요 |

## 3. 시스템 아키텍처

### 3.1 논리 구성

```text
[고객 Android 앱] ─┐
                   ├─ HTTPS ─ [백엔드 API] ─ [PostgreSQL]
[관리자 웹/모바일] ┘              │    ├──── [Redis]
                                  │    └──── [파일 저장소]
                                  │
                                  ├─ [결제 서비스]
                                  ├─ [푸시·문자 서비스]
                                  ├─ [주소·지도 서비스]
                                  └─ [백그라운드 작업]
```

### 3.2 백엔드 모듈

| 모듈 | 책임 |
| --- | --- |
| 인증·권한 | 고객 및 관리자 인증, 토큰, 역할별 접근 제어 |
| 고객 | 고객 프로필, 배송지, 동의 정보 관리 |
| 카탈로그 | 세탁 품목, 옵션, 가격, 주의사항 관리 |
| 예약 | 서비스 지역, 영업일, 시간대, 예약 가능 수량 관리 |
| 주문 | 주문 생성, 변경, 취소, 금액 계산, 상태 전이 |
| 검수 | 실제 품목, 사진, 변경 사유, 최종 금액 관리 |
| 배차·배송 | 수거·배송 일정, 담당자 배정, 완료 증빙 관리 |
| 세탁 작업 | 세탁 대기·진행·완료 및 내부 메모 관리 |
| 결제 | 결제 승인, 실패, 취소, 환불 및 대사 관리 |
| 알림 | 푸시·문자 발송, 템플릿, 발송 결과 관리 |
| 문의·사고 | 고객 문의, 재세탁, 분실, 훼손, 보상 관리 |
| 운영 설정 | 관리자, 권한, 쿠폰, 공지 및 서비스 정책 관리 |
| 통계 | 주문, 매출, 취소, 환불 및 운영 지표 집계 |
| 감사 로그 | 중요 데이터의 조회 및 변경 이력 보관 |

### 3.3 초기 배포 방식

- 백엔드는 모듈형 모놀리스 구조로 시작한다.
- API 서버와 백그라운드 작업 프로세스는 논리적으로 분리한다.
- 개발, 테스트, 운영 환경을 분리한다.
- 데이터베이스 스키마 변경은 버전 관리되는 마이그레이션으로 수행한다.
- 운영 서버는 최소 2개 인스턴스로 구성할 수 있도록 무상태 API로 설계한다.
- 파일은 서버 로컬 디스크가 아닌 오브젝트 스토리지에 저장한다.

## 4. 사용자 및 권한 설계

### 4.1 고객 인증

- 휴대전화 본인 인증 후 고객 계정을 생성하는 방식을 기본안으로 한다.
- 로그인 성공 시 짧은 수명의 액세스 토큰과 갱신 토큰을 발급한다.
- 갱신 토큰은 서버에서 폐기 가능해야 하며 로그아웃·탈퇴 시 무효화한다.
- 기기별 푸시 토큰을 저장하고 만료된 토큰을 정리한다.

### 4.2 관리자 인증

- 관리자 계정은 최고 관리자가 생성하거나 승인한다.
- 관리자 계정에는 강력한 비밀번호 정책을 적용한다.
- 최고 관리자에는 다중 인증 적용을 권장한다.
- 반복 로그인 실패 시 계정을 일정 시간 잠근다.
- 관리자 세션 만료 시간은 고객보다 짧게 설정한다.

### 4.3 역할별 권한

| 기능 | 최고 관리자 | 일반 관리자 | 수거·배송 담당자 |
| --- | --- | --- | --- |
| 운영 설정 및 관리자 관리 | 전체 | 불가 | 불가 |
| 주문 조회 | 전체 | 전체 또는 지점 범위 | 배정 주문 중심 |
| 주문·가격 수정 | 가능 | 권한에 따라 가능 | 불가 |
| 검수 등록 | 가능 | 가능 | 권한 부여 시 가능 |
| 수거·배송 배정 | 가능 | 가능 | 불가 |
| 수거·배송 상태 변경 | 가능 | 가능 | 배정 주문만 가능 |
| 결제·환불 처리 | 가능 | 별도 권한 필요 | 불가 |
| 고객 개인정보 조회 | 가능 | 업무 범위만 | 배정 업무에 필요한 범위만 |
| 통계 조회 | 가능 | 권한에 따라 가능 | 불가 |

권한은 역할 기반 접근 제어를 사용하되, 환불·개인정보·관리자 관리 등 민감 기능은 별도 권한으로 세분화한다.

## 5. 핵심 업무 흐름

### 5.1 주문 신청

1. 고객이 배송지를 선택한다.
2. 서버가 서비스 가능 지역인지 확인한다.
3. 고객이 품목, 수량, 옵션 및 요청사항을 입력한다.
4. 서버가 현재 가격표를 기준으로 예상 금액을 계산한다.
5. 고객이 수거 시간대를 선택한다.
6. 서버가 해당 시간대의 예약 가능 수량을 다시 확인한다.
7. 고객이 주문을 확정하면 주문번호를 발급하고 가격 명세의 사본을 저장한다.
8. 관리자에게 신규 주문 알림을 발송한다.

클라이언트가 전달한 금액을 신뢰하지 않고 서버가 최종 계산한다.

### 5.2 수거 및 검수

1. 관리자가 주문을 접수하고 담당자를 배정한다.
2. 담당자가 수거 시작과 완료 상태를 등록한다.
3. 담당자 또는 관리자가 실제 품목, 수량, 오염 상태 및 사진을 등록한다.
4. 서버가 검수 기준으로 최종 금액을 계산한다.
5. 신청 금액과 차이가 있거나 정책상 승인이 필요한 경우 `고객 승인 대기`로 변경한다.
6. 고객 승인 후 결제 또는 세탁 단계로 진행한다.
7. 고객이 거절하면 관리자 협의 또는 취소 절차로 전환한다.

### 5.3 세탁 및 배송

1. 결제 정책 조건이 충족된 주문을 `세탁 대기`로 변경한다.
2. 작업 시작 시 `세탁 중`, 완료 시 `세탁 완료`로 변경한다.
3. 관리자가 배송 일정과 담당자를 배정한다.
4. 담당자가 배송 시작 상태를 등록한다.
5. 사진, 서명 또는 인증번호로 완료 증빙을 등록한다.
6. 서버가 주문을 `배송 완료`로 변경하고 고객에게 알린다.

### 5.4 결제 및 환불

- 결제 요청마다 중복 방지 키를 사용한다.
- 결제 서비스의 승인 결과와 서버의 주문 금액이 일치하는지 검증한다.
- 앱 응답과 별개로 결제사의 웹훅을 검증하여 최종 상태를 반영한다.
- 웹훅 서명과 요청 출처를 검증하고 같은 이벤트의 중복 처리를 방지한다.
- 부분 환불과 전체 환불을 구분하며 누적 환불액이 결제액을 넘지 않게 한다.
- 결제·환불 데이터 변경과 관리자 작업은 감사 로그에 기록한다.

## 6. 주문 상태 설계

### 6.1 정상 상태 전이

```text
신청 접수
  → 주문 확인
  → 수거 예정
  → 수거 중
  → 수거 완료
  → 품목 검수
  → 고객 승인 대기 (필요한 경우)
  → 결제 대기 (결제 정책에 따라 위치 변경 가능)
  → 세탁 대기
  → 세탁 중
  → 세탁 완료
  → 배송 예정
  → 배송 중
  → 배송 완료
```

### 6.2 예외 전이

- 신청 접수 또는 주문 확인 → 주문 거절
- 배송 완료 전 허용 상태 → 주문 취소 또는 취소 요청
- 수거 예정 또는 수거 중 → 수거 실패 → 재예약 또는 주문 취소
- 결제 대기 → 결제 실패 → 결제 재시도 또는 주문 취소
- 모든 진행 상태 → 처리 보류 → 직전 업무 단계 또는 주문 취소
- 배송 완료 → 재세탁 → 세탁 중 → 배송 예정
- 결제 완료 후 취소·보상 → 환불 진행 → 환불 완료

### 6.3 상태 변경 규칙

- 상태 전이 가능 여부는 서버에서 검증한다.
- 고객, 관리자, 담당자별로 허용된 상태 변경만 처리한다.
- 모든 변경에 이전 상태, 다음 상태, 변경자, 사유 및 시간을 기록한다.
- 동일 주문을 동시에 수정할 경우 버전 번호를 이용한 낙관적 잠금을 적용한다.
- 상태 변경과 이력 저장은 하나의 데이터베이스 트랜잭션에서 처리한다.
- 상태 변경 후 알림은 트랜잭션 완료 뒤 비동기로 발송한다.

## 7. 데이터베이스 설계

### 7.1 공통 규칙

- 기본키는 외부 추측이 어려운 UUID 또는 시간 정렬형 UUID를 사용한다.
- 모든 일시는 데이터베이스에 UTC로 저장하고 화면에서 한국 시간으로 표시한다.
- 금액은 부동소수점이 아닌 정수 원 단위로 저장한다.
- 주요 테이블에 `created_at`, `updated_at`, 필요 시 `deleted_at`을 둔다.
- 고객 화면에 노출되는 주문번호는 내부 기본키와 분리한다.
- 주문 당시의 주소, 품목명, 단가 및 할인 조건은 사본으로 보관한다.

### 7.2 주요 테이블

#### customers

| 필드 | 설명 |
| --- | --- |
| id | 고객 식별자 |
| phone | 휴대전화 번호, 암호화 또는 마스킹 대상 |
| name | 고객명 |
| status | ACTIVE, SUSPENDED, WITHDRAWN |
| marketing_consent | 마케팅 수신 동의 여부 |
| last_login_at | 마지막 로그인 시간 |

#### customer_addresses

| 필드 | 설명 |
| --- | --- |
| id | 배송지 식별자 |
| customer_id | 고객 식별자 |
| label | 집, 회사 등 배송지 이름 |
| postal_code | 우편번호 |
| address | 기본 주소 |
| address_detail | 상세 주소 |
| entrance_note | 공동현관 출입 정보 |
| delivery_note | 수거·배송 요청사항 |
| is_default | 기본 배송지 여부 |
| service_area_id | 서비스 지역 식별자 |

#### admin_users / roles / permissions

- 관리자 기본 정보와 상태를 `admin_users`에 저장한다.
- 역할과 권한을 별도 테이블로 관리한다.
- 다지점 도입 가능성을 위해 관리자에게 선택적으로 지점 범위를 연결할 수 있게 한다.

#### service_areas / service_slots

- `service_areas`: 행정구역, 우편번호 또는 영역 기준의 서비스 가능 지역
- `service_slots`: 날짜·시간대, 수거 또는 배송 구분, 최대 수량, 예약 수량, 마감 상태
- 시간대 예약 시 동시 신청으로 정원을 넘지 않도록 행 잠금 또는 원자적 갱신을 사용한다.

#### product_categories / products / product_options

| 테이블 | 주요 내용 |
| --- | --- |
| product_categories | 의류, 침구 등 품목 분류 |
| products | 품목명, 기본 가격, 노출 상태, 주의사항 |
| product_options | 옵션명, 추가 가격, 적용 가능 품목 |
| price_histories | 가격 적용 시작일·종료일 및 변경 이력 |

#### order_items / order_item_options

- 주문 당시 품목명, 단가, 수량 및 옵션 가격의 사본을 저장한다.
- 고객 신청 수량과 검수 확정 수량을 구분한다.
- 품목별 예상 금액과 최종 금액을 저장한다.
- 취급 주의사항과 검수 메모를 저장한다.

#### inspections / attachments

- `inspections`: 검수 담당자, 검수 시간, 변경 사유, 고객 승인 필요 여부
- `attachments`: 주문·검수·문의·배송 증빙 파일의 저장 위치, 유형, 크기 및 등록자
- 파일 접근은 만료 시간이 있는 서명 URL을 사용한다.

- 주문, 업무 유형(PICKUP 또는 DELIVERY), 담당자, 예정 시간, 시작·완료 시간과 실패 사유를 저장한다.
- 담당자는 본인에게 배정된 업무만 변경할 수 있다.

#### payments / refunds / payment_events

- `payments`: 결제 주문, 결제사 거래번호, 결제 수단, 요청·승인·취소 금액과 상태
- `refunds`: 원 결제, 환불 금액, 사유, 처리자 및 상태
- `payment_events`: 결제사 웹훅 원본 식별자와 처리 결과
- 카드번호와 같은 민감한 결제정보는 직접 저장하지 않는다.

#### coupons / coupon_issues / order_discounts

- 쿠폰 정책, 고객별 발급, 사용 여부와 주문에 실제 적용된 할인 사본을 구분하여 저장한다.

#### inquiries / incident_cases

- 문의 유형, 주문, 담당자, 상태, 고객 내용과 관리자 답변을 저장한다.
- 재세탁·분실·훼손 사고에는 증빙, 보상 금액 및 처리 결과를 추가로 저장한다.

#### notifications

- 수신자, 채널, 템플릿, 발송 상태, 실패 사유, 외부 메시지 식별자와 발송 시간을 저장한다.

#### audit_logs

- 관리자 로그인, 개인정보 조회, 가격 수정, 주문 강제 변경, 환불, 권한 변경 등을 기록한다.
- 감사 로그는 일반 관리자가 수정하거나 삭제할 수 없게 한다.

## 8. API 설계

### 8.1 공통 규칙

- 기본 경로는 `/api/v1`으로 한다.
- 요청과 응답은 JSON을 기본으로 한다.
- 목록 API는 페이지 번호 또는 커서 기반 페이지 처리를 제공한다.
- 날짜·시간은 ISO 8601 형식을 사용한다.
- 생성·결제 등 중복 위험 요청은 `Idempotency-Key` 헤더를 지원한다.
- API 오류는 공통 오류 코드, 사용자 메시지, 추적 식별자를 반환한다.
- 관리자 API는 `/api/v1/admin` 경로로 분리한다.

### 8.5 파일 업로드

1. 클라이언트가 파일명, 크기 및 콘텐츠 유형으로 업로드 URL을 요청한다.
2. 서버가 허용된 확장자와 크기를 검사하고 일회성 서명 URL을 발급한다.
3. 클라이언트가 파일 저장소에 직접 업로드한다.
4. 클라이언트가 업로드 완료 API를 호출한다.
5. 서버가 실제 파일을 확인한 후 주문 또는 문의에 연결한다.

이미지 크기 제한, 허용 형식, 악성 파일 검사 및 보관 기간을 운영 정책으로 확정한다.

## 9. 화면 및 클라이언트 설계

### 9.1 고객 Android 앱

- 화면 계층은 로그인, 홈, 주문 신청, 주문 조회, 알림, 문의, 내 정보 영역으로 구분한다.
- 주문 신청은 배송지 → 품목·옵션 → 일정 → 예상 금액 확인 → 결제 또는 신청 완료 순서로 구성한다.
- 진행 중 주문은 현재 상태와 다음 예상 단계를 우선 표시한다.
- 네트워크 재시도 시 주문과 결제가 중복되지 않도록 같은 중복 방지 키를 재사용한다.
- 민감한 토큰은 Android 보안 저장소에 저장한다.
- 푸시 알림 선택 시 해당 주문 또는 문의 화면으로 바로 이동한다.

### 9.2 관리자 웹

- PC에서는 검색·필터와 목록·상세를 함께 확인할 수 있는 업무 중심 화면으로 구성한다.
- 태블릿에서는 주요 작업 버튼과 표의 핵심 열을 우선 노출한다.
- 주문 목록의 필터 조건은 URL에 반영하여 새로고침과 공유가 가능하게 한다.
- 위험 작업인 환불, 주문 강제 취소, 가격 변경에는 확인 단계와 사유 입력을 적용한다.
- 개인정보는 기본적으로 마스킹하고 권한과 업무 필요에 따라 전체 표시한다.

### 9.3 관리자 모바일

- 초기에는 관리자 웹을 반응형으로 제공하는 방안을 권장한다.
- 하단 메뉴는 오늘의 업무, 주문 검색, 알림, 내 정보 중심으로 구성한다.
- 수거·배송 업무 화면에서 전화, 지도 연결, 상태 변경, 사진 등록을 최소 단계로 제공한다.
- 통신이 불안정할 경우 임시 저장 여부를 표시하되, 상태 변경 완료로 오인되지 않게 한다.
- 완전한 오프라인 업무 처리는 MVP에서 제외하고 추후 필요성을 검토한다.

## 10. 알림 설계

### 10.1 발송 방식

- 주문 상태 변경 트랜잭션에서 발송 대상 이벤트를 별도 테이블에 저장한다.
- 백그라운드 작업이 이벤트를 읽어 푸시 또는 문자를 발송한다.
- 발송 실패 시 제한 횟수만큼 재시도하고 최종 실패 사유를 기록한다.
- 같은 이벤트와 수신자 조합의 중복 발송을 방지한다.

### 10.2 주요 이벤트

- 주문 접수 및 관리자 확인
- 수거 예정, 수거 시작 및 완료
- 검수 완료와 최종 금액 승인 요청
- 결제 성공, 실패, 취소 및 환불
- 세탁 시작, 완료 및 지연
- 배송 시작, 완료 및 실패
- 주문 거절, 취소, 처리 보류 및 재세탁
- 문의 답변 등록

### 10.3 알림 설정

- 거래·업무상 필수 알림과 마케팅 알림을 구분한다.
- 마케팅 알림은 고객 동의 여부와 허용 시간을 확인한다.
- 알림 문구에는 필요 이상의 개인정보를 포함하지 않는다.

## 11. 외부 서비스 연동

| 연동 | 용도 | 필수 처리 |
| --- | --- | --- |
| 결제대행사 | 결제, 취소, 환불 | 웹훅 검증, 중복 방지, 거래 대사 |
| FCM | Android 푸시 | 토큰 갱신, 실패 토큰 제거 |
| 문자 서비스 | 중요 알림 및 인증 | 발송 결과 저장, 비용·재시도 관리 |
| 주소 검색 | 주소 표준화 및 우편번호 | 주소 사본 저장, 장애 시 처리 |
| 지도·길찾기 | 담당자 경로 확인 | 앱 간 연결 또는 지도 SDK 사용 |
| 본인 인증 | 고객 휴대전화 인증 | 인증 결과 검증 및 최소 정보 저장 |

각 연동은 인터페이스 계층으로 감싸 공급업체 변경이 핵심 업무 코드에 영향을 적게 주도록 한다.

## 12. 보안 설계

- 모든 외부 통신에 HTTPS를 적용한다.
- 비밀번호는 검증된 단방향 해시 알고리즘으로 저장한다.
- API 입력값의 형식, 길이, 범위와 권한을 서버에서 검증한다.
- SQL 삽입, 스크립트 삽입, 요청 위조 및 무차별 대입 공격 방어를 적용한다.
- 인증과 결제 API에는 요청 횟수 제한을 적용한다.
- 개인정보 필드는 저장 시 암호화하고 로그에는 평문으로 기록하지 않는다.
- 운영 비밀값은 소스 저장소가 아닌 비밀 관리 시스템에 저장한다.
- 파일 접근에는 짧은 만료 시간의 서명 URL을 사용한다.
- 데이터 내려받기, 환불, 권한 변경 등 민감 작업은 감사 로그를 남긴다.
- 운영 관리자 권한은 최소 권한 원칙으로 부여하고 퇴사·역할 변경 시 즉시 회수한다.
- 의존성 취약점과 Android·웹 보안 설정을 배포 전에 검사한다.

## 13. 성능 및 안정성 설계

### 13.1 목표 초안

- 일반 조회 API의 95%는 정상 부하에서 2초 이내 응답을 목표로 한다.
- 주문 생성과 상태 변경 API의 95%는 외부 연동 시간을 제외하고 3초 이내 처리를 목표로 한다.
- 이미지 원본은 목록에서 직접 내려받지 않고 크기가 조정된 이미지를 사용한다.
- 주문 목록의 자주 사용하는 검색 조건에 데이터베이스 인덱스를 구성한다.

구체적인 동시 사용자 수와 주문량이 확정되면 부하 목표를 보완한다.

### 13.2 장애 대응

- 외부 서비스 호출에는 시간 제한, 제한된 재시도 및 장애 격리를 적용한다.
- 결제 결과가 불명확하면 성공으로 처리하지 않고 결제사 조회로 상태를 확인한다.
- 알림 장애가 주문 상태 변경을 실패시키지 않도록 비동기로 분리한다.
- 데이터베이스 백업을 자동화하고 정기적으로 복구 훈련을 수행한다.
- 장애 발생 시 요청 식별자로 앱, API, 외부 연동 로그를 연결하여 조회할 수 있게 한다.

## 14. 로그 및 모니터링

- API 요청 시간, 결과 코드, 요청 식별자와 사용자 유형을 구조화 로그로 기록한다.
- 인증 토큰, 비밀번호, 카드 정보, 상세 주소 및 전화번호는 로그에서 제거하거나 마스킹한다.
- 오류율, 응답 시간, 서버 자원, 데이터베이스 연결, 작업 큐 적체를 수집한다.
- 결제 실패 급증, 알림 적체, 예약 초과 및 서버 오류 급증에 경보를 설정한다.
- 주문 상태별 체류 시간을 측정하여 지연 주문을 탐지한다.

## 15. 배치 및 예약 작업

- 고객 최종 금액 승인 기한 만료 주문 탐지
- 미결제 주문의 만료 또는 재알림
- 수거·배송 예정 알림 발송
- 장시간 상태가 바뀌지 않은 지연 주문 탐지
- 실패한 알림의 제한적 재시도
- 만료된 인증·푸시 토큰 정리
- 일별 매출 및 주문 통계 집계
- 개인정보 및 파일 보관 기간에 따른 정리
- 결제사 거래 내역과 내부 결제 데이터 대사

모든 작업은 여러 서버에서 동시에 실행되어도 한 번만 처리되도록 잠금 또는 작업 식별자를 사용한다.

## 16. 테스트 전략

### 16.1 자동화 테스트

- 단위 테스트: 금액 계산, 할인, 상태 전이, 취소 가능 조건
- 통합 테스트: 데이터베이스 트랜잭션, 권한, 주문 생성 및 검수
- 계약 테스트: Android·웹과 백엔드의 API 형식
- 외부 연동 테스트: 결제 웹훅, 푸시 및 문자 실패 처리
- UI 테스트: 고객 주문 신청과 관리자 핵심 처리 흐름
- 보안 테스트: 인증 우회, 다른 고객 주문 접근, 관리자 권한 검증
- 부하 테스트: 예약 시간대 동시 신청, 주문 목록, 상태 변경

### 16.2 필수 시나리오

1. 고객이 정상 주문을 신청하고 배송 완료까지 처리한다.
2. 두 고객이 마지막 예약 자리를 동시에 신청해도 한 건만 확정된다.
3. 중복 주문 요청이 같은 주문을 두 개 생성하지 않는다.
4. 검수 후 가격이 변경되어 고객 승인과 결제가 진행된다.
5. 허용되지 않은 상태 전이가 거부되고 기존 상태가 유지된다.
6. 결제 응답이 끊겨도 웹훅과 조회를 통해 한 번만 승인 처리된다.
7. 부분 환불 누계가 결제 금액을 초과하지 않는다.
8. 담당자가 다른 담당자의 배정 업무를 변경할 수 없다.
9. 고객이 다른 고객의 주문, 주소 및 사진에 접근할 수 없다.
10. 알림 발송 실패가 주문 처리 결과를 되돌리지 않는다.
11. 수거 실패 후 재예약하거나 주문을 취소할 수 있다.
12. 배송 완료 증빙 없이 완료 처리가 가능한지 정책에 따라 검증한다.

## 17. 배포 및 운영

### 17.1 환경

| 환경 | 목적 |
| --- | --- |
| Local | 개발자 로컬 개발 |
| Development | 기능 통합 및 내부 확인 |
| Staging | 운영과 유사한 최종 검증 |
| Production | 실제 서비스 운영 |

- 환경별 데이터베이스와 외부 서비스 인증 정보를 분리한다.
- 개발·테스트 환경에서는 실제 고객에게 문자나 푸시가 발송되지 않게 한다.
- 운영 데이터는 개발 환경으로 그대로 복사하지 않는다.

### 17.2 배포 절차

1. 코드 정적 검사와 자동화 테스트를 수행한다.
2. 애플리케이션 및 데이터베이스 변경 사항을 검토한다.
3. 테스트 환경에서 마이그레이션과 핵심 시나리오를 검증한다.
4. 운영 배포 전 데이터베이스 백업과 복구 가능 여부를 확인한다.
5. 점진적으로 배포하고 오류율과 응답 시간을 관찰한다.
6. 이상 발생 시 애플리케이션을 이전 버전으로 되돌린다.

데이터베이스 변경은 이전 애플리케이션 버전과 일정 기간 호환되도록 단계적으로 적용한다.

## 18. 개발 단계

### 18.1 1단계: 기반 구축

- 프로젝트와 개발·배포 환경 구성
- 고객 및 관리자 인증·권한
- 품목, 가격, 서비스 지역과 시간대 관리
- 공통 오류, 로그, 파일 업로드 및 API 문서

### 18.2 2단계: 주문 핵심 기능

- 고객 배송지와 서비스 신청
- 서버 기준 예상 금액 계산
- 관리자 주문 접수와 상세 관리
- 주문 상태 전이와 이력
- 푸시 알림 기본 구조

### 18.3 3단계: 현장 및 세탁 업무

- 담당자 배정과 수거·배송 일정
- 관리자 모바일 현장 화면
- 검수, 사진 및 최종 금액 승인
- 세탁 진행과 배송 완료 증빙

### 18.4 4단계: 결제 및 고객 지원

- 결제, 웹훅, 취소 및 환불
- 문의, 사고 및 재세탁 처리
- 공지와 문자 알림
- 영수증과 기본 통계

### 18.5 5단계: 안정화 및 출시

- 전체 업무 시나리오 테스트
- 보안, 권한 및 개인정보 점검
- 부하 테스트와 장애 복구 점검
- 운영자 교육 및 운영 매뉴얼 작성
- Android 앱 배포와 운영 모니터링 구성

## 19. 확정이 필요한 기술·운영 사항

개발 착수 전에 다음 내용을 제품 책임자와 개발 담당자가 함께 확정해야 한다.

1. 고객 인증 방식과 본인 인증 업체
2. 비회원 주문 지원 여부
3. 선결제, 검수 후 결제 또는 혼합 결제 방식
4. 결제대행사와 지원할 결제 수단
5. 관리자 모바일을 반응형 웹으로 제공할지 별도 앱으로 개발할지
6. 주소 검색, 지도, 문자 서비스 제공 업체
7. 최종 금액 고객 승인 조건과 응답 만료 처리
8. 주문 변경·취소·환불 가능 조건
9. 예약 시간대의 단위와 최대 처리 건수
10. 배송 완료 증빙 방식
11. 사진 파일의 최대 크기, 형식 및 보관 기간
12. 관리자 역할별 상세 권한
13. 개인정보, 주문, 결제, 감사 로그의 보관 기간
14. 다지점 운영 도입 시점과 지점별 데이터 접근 범위
15. 예상 일 주문량, 동시 사용자 수 및 서비스 가용성 목표
16. 클라우드·서버 운영 업체와 장애 대응 담당자

## 20. MVP 완료 기준

다음 조건을 모두 만족하면 초기 출시 기능이 완료된 것으로 판단한다.

- 고객이 Android 앱에서 가입, 배송지 등록, 주문 신청 및 결제를 완료할 수 있다.
- 고객이 주문의 최신 상태, 최종 금액, 결제 및 알림 내역을 확인할 수 있다.
- 관리자가 웹에서 품목·가격·지역·시간대·주문·고객을 관리할 수 있다.
- 관리자가 웹 또는 모바일에서 검수, 담당자 배정, 세탁 및 배송 상태를 처리할 수 있다.
- 수거·배송 담당자가 모바일에서 배정 업무와 완료 증빙을 처리할 수 있다.
- 결제 실패, 수거 실패, 주문 취소, 환불 및 재세탁 예외 흐름을 처리할 수 있다.
- 역할별 권한이 적용되고 주문·결제·민감 작업 이력이 기록된다.
- 중복 주문과 중복 결제가 방지되고 필수 자동화 테스트가 통과한다.
- 백업, 모니터링, 장애 알림 및 운영자 대응 절차가 준비되어 있다.
